# Puntaje Estimado /699 — Design Spec

Slice 3 of the original Modo Examen decomposition (5 slices total, per the
brainstorming that produced slices 1-2). Slice 1 (sets generables) and
slice 2 (Runner lockstep) are complete and merged to `main`. This is the
smallest possible cut of the original Fase C ("Resultados y bitácora")
spec — everything else Fase C described (audio re-listen during review,
per-question timing instrumentation, failure-cause tagging, persisted
session history, export, a progress-over-time graph) is deliberately out
of scope here and left for later slices.

## Purpose

`ExamSummary.jsx` (built in slice 2) already shows a raw correct/total
count and a per-section breakdown at the end of an exam attempt. It has no
sense of how that raw count relates to the real TEFAQ's official 0-699
scale, which is the number a candidate actually cares about. This slice
adds a clearly-labeled, non-official linear estimate of that score, plus
the B2 threshold (raw score 400) expressed both as an estimated score and
as an equivalent "you need N/36 correct" operational metric — matching how
the original spec described the "~23+/40 ≈ B2" heuristic, recalibrated for
the 36-question `SET_STANDARD_36` format that's actually implemented
(the original spec assumed 40; pilotes and the 40-question path were
explicitly descoped in slice 1/2).

## Scope

**In scope:**
- A pure module, `examScoring.js`, computing the `/699` estimate and the
  B2 threshold from `correctTotal`/`totalQuestions` — nothing else.
- `ExamSummary.jsx` renders the estimate, a B2-cleared/not-yet badge, and
  the equivalent raw-count threshold, alongside what it already shows.

**Explicitly out of scope (left for later slices):**
- **Audio re-listening during review.** A slice-2 fix (in response to PR
  review) makes `ExamMode.jsx` revoke every preloaded audio blob URL the
  moment `handleComplete` fires — deliberately, to close a resource leak.
  Fase C's original "re-listen to audio during review" requirement
  directly conflicts with that: it needs the audio kept alive past
  completion. Resolving that conflict (keeping audio alive through a
  review screen, releasing only when truly leaving) is real design work
  belonging to whichever slice adds the review screen, not this one.
- **Per-question analytics** (time-to-first-selection, number of answer
  changes, distractor-hit tracking). `examMachine.js`'s `ANSWER_SELECTED`
  handling only stores the current selected option per question — it
  doesn't timestamp anything. Adding that requires touching the already
  reviewed, already-tested lockstep reducer from slice 2, which is exactly
  the kind of "not just adding a screen" change this slice deliberately
  avoids.
- **Failure-cause tagging**, **persisted session history**
  (`backend/data/sessions/`), **export**, and the **progress-over-time
  graph** — all backend-touching, all substantially larger than a score
  estimate, all left for a dedicated future slice.
- Piloted sets (`pilotes: true`, 40 questions with 4 unscored). The runner
  built in slice 2 already refuses these outright (`setCompatibility.js`)
  before an attempt can even start, so this slice's formula only ever
  needs to handle the compatible case: exactly 36 questions. It's still
  written in terms of `totalQuestions` rather than a hardcoded 36 (see
  Architecture) so it isn't quietly wrong if that ever changes, but
  supporting a *different* total on purpose is not a goal here.

**No backend changes.** This slice reads only what `ExamSummary` already
receives as props (`correctTotal`, `totalQuestions`, `correctBySection`,
`totalsBySection`) — all computed client-side today from `examMachine.js`'s
`computeResults`. Nothing new is fetched, generated, or persisted.

## Formula

The real TEFAQ 0-699 conversion is a non-public psychometric scaling — the
original spec was explicit that any number shown here must be labeled as a
rough linear estimate, never presented as an official score. The
calibration point that spec gave was "~23+/40 correct ≈ B2" against a raw
score threshold of 400/699 — i.e., B2 lands at roughly 400/699 ≈ 57.2% of
the scale, and 23/40 = 57.5% was that spec's approximation of the same
cutoff for a 40-question set.

Since the implemented set format is 36 questions, not 40, this slice keeps
the same *percentage* (≈57.2%) and recalibrates the raw-count threshold
against 36 instead of re-deriving a new percentage from scratch:

```js
export function estimateScore699(correctTotal, totalQuestions) {
  if (!Number.isInteger(totalQuestions) || totalQuestions <= 0) {
    throw new Error(`totalQuestions inválido: ${totalQuestions}`);
  }
  if (!Number.isInteger(correctTotal) || correctTotal < 0 || correctTotal > totalQuestions) {
    throw new Error(`correctTotal inválido: ${correctTotal}`);
  }
  const estimated699 = Math.round((correctTotal / totalQuestions) * 699);
  const isB2 = estimated699 >= 400;
  const thresholdCount = Math.ceil((400 / 699) * totalQuestions);
  return { estimated699, isB2, thresholdCount };
}
```

For `totalQuestions = 36`: `thresholdCount = Math.ceil(0.5722... * 36) = 21`
— i.e. "necesitás ~21/36 aciertos para B2", the direct analogue of the
original spec's "~23+/40". The function takes `totalQuestions` as a
parameter rather than hardcoding 36 so it keeps producing a consistent
answer if the compatible format ever changes — not because supporting a
different total is a goal of this slice.

`correctTotal`/`totalQuestions` always come from `computeResults`
(slice 2), which can only ever produce valid integers in range — so the
validation above is a defensive contract check, not a real user-facing
error path. It throws rather than silently clamping or returning `null`,
consistent with this module staying strict about its inputs the way
`examMachine.js`'s reducer is strict about its event shapes.

## Architecture

- **`frontend/src/exam/examScoring.js`** (new) — pure, no DOM, no
  dependencies. Exports `estimateScore699(correctTotal, totalQuestions) ->
  { estimated699: number, isB2: boolean, thresholdCount: number }`.
  Unit-tested with `node --test`, following the same pattern as
  `examTiming.js`/`examMachine.js`/`setCompatibility.js` from slice 2.
- **`frontend/src/exam/ExamSummary.jsx`** (modified) — imports
  `estimateScore699` and calls it with the `correctTotal`/`totalQuestions`
  props it already receives (no new props needed). Renders, alongside the
  existing raw correct/total and per-section breakdown:
  - The estimate itself, e.g. "≈ 524/699" (27/36 correct), visually secondary to the raw
    count (which stays the primary, unambiguous number) and explicitly
    labeled as a non-official linear estimate.
  - A B2 badge: cleared (green) or not-yet (amber), driven by `isB2`.
  - The operational metric, always visible regardless of pass/fail: e.g.
    "necesitás 21/36 aciertos para B2", using `thresholdCount`.

No other file changes. `ExamMode.jsx`, `ExamRunner.jsx`, `examMachine.js`,
and every other slice-2 file are untouched.

## Testing

`examScoring.test.js` (new), `node --test`, covering:

- **Boundary cases at 36 questions:** `0/36 → 0`; `36/36 → 699`;
  `20/36 → 388, isB2 false`; `21/36 → 408, isB2 true`.
- **`thresholdCount === 21`** for `totalQuestions = 36`, the documented
  calibration point.
- **Invariant, `totalQuestions = 36`:** `0 <= estimated699 <= 699` for
  every valid `correctTotal` from `0` to `36`, not just the boundary cases
  above (loop over the full range rather than spot-checking).
- **Badge/threshold consistency, `totalQuestions = 36`:**
  `correctTotal === thresholdCount - 1` (i.e. `20`) yields `isB2 === false`,
  and `correctTotal === thresholdCount` (i.e. `21`) yields `isB2 === true`
  — confirming `thresholdCount` is genuinely the exact minimum passing
  count the formula itself produces at 36, not just a number that happens
  to look right. This is checked at 36 specifically, not asserted as a
  property that holds for every possible `totalQuestions`: `Math.round`
  and `Math.ceil` interacting can in principle put `thresholdCount - 1`
  within rounding distance of the 400 cutoff for some totals (it doesn't
  for 36, which is the only total this app produces per the Scope
  section), so this isn't a general mathematical guarantee to rely on if
  a different `totalQuestions` is ever supported.
- **Rejects invalid input:** `totalQuestions` of `0`, a negative number,
  or a non-integer (decimal) all throw; `correctTotal` negative, a
  non-integer, or greater than `totalQuestions` all throw.

`ExamSummary.jsx` remains browser-verified only, consistent with the rest
of the frontend (no test runner exists for React components in this repo).

## Open Decisions Log

1. Scope narrowed to score-display-only; audio review, per-question
   analytics, failure tagging, and persisted history are explicitly
   deferred — the user's own choice when presented with the full
   Fase C scope and the audio-retention conflict.
2. The `/699` formula keeps the original spec's ~57.2% B2 percentage but
   recalibrates the raw threshold from 40 to 36 questions, per the user's
   explicit choice over supplying a different formula from personal
   knowledge of the real exam.
3. `estimateScore699` takes `totalQuestions` as a parameter rather than a
   hardcoded 36, since the codebase's existing convention (`ExamSummary`
   already computes `totalQuestions` from the set rather than assuming a
   constant) argues against introducing a new magic number — not because
   a different total is an intended use case for this slice.
